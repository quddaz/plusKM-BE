# MySQL 공간 검색 벤치마크 결과

측정일: 2026-09-29  
리전: ap-northeast-2  
백엔드: EC2 t4g.small / Spring Boot / Java 21  
DB: RDS MySQL 8.4.9 / db.t4g.micro / gp3  
부하 발생기: EC2 c7i-flex.large / k6 2.2.0

## 데이터 및 방식

- 응급실 530개, 활성 528개, 좌표 530개
- 모든 좌표는 SRID 4326이며 NULL 좌표는 없음
- 각 회차는 10 VU로 60초 워밍업 후 25 VU로 180초 측정
- 기존/정확반경 비교는 순서 편향을 줄이기 위해 ABBA 순서로 실행
- 각 회차 사이 30초 쿨다운
- k6 HTTP, Actuator Prometheus, JVM, Spring HTTP, HikariCP, EC2 sar/pidstat, MySQL 전역 상태, RDS CloudWatch를 수집

## 구현 비교

| 방식 | 쿼리 | 서울 10km 결과 |
|---|---|---:|
| 기존 | `ST_Within` 사각형 | 59개 |
| 동일결과 인덱스형 | `MBRContains` 사각형 + SPATIAL INDEX | 59개 |
| 정확반경형 | MBR 후보 + `ST_Distance_Sphere` + 거리 정렬 | 46개 |

운영 DB에는 누락되어 있던 `SPATIAL INDEX idx_emergency_coordinate (coordinate)`를 생성했다. 인덱스 생성 후 기존 `ST_Within` 쿼리도 MySQL 옵티마이저가 동일한 공간 인덱스 범위 스캔을 사용한다.

## MySQL 실행계획

- 기존: 공간 인덱스 후보 스캔 약 0.34ms, 전체 필터 약 1.56ms
- 동일결과 인덱스형: 공간 인덱스 후보 스캔 약 0.34ms, 전체 필터 약 1.73ms
- 정확반경형: 후보 스캔 약 0.30ms, 거리 필터 약 5.11ms, 정렬 포함 약 6.17ms

병목은 공간 인덱스 후보 추출이 아니라 `ST_Distance_Sphere` 계산과 거리 정렬이다.

## EC2 / 부하 발생기

- 백엔드 EC2 전체 혼합 구간 평균 idle 60.34% (2 vCPU 합산)
- 동일결과 집중 구간 평균 idle 51.91%
- k6 EC2 평균 idle 93.56%로 부하 발생기는 병목이 아님
- 백엔드 Java 프로세스의 디스크 읽기/쓰기는 매우 낮아 애플리케이션 디스크 병목이 아님

## RDS / MySQL

- RDS CPU 최고 94.8%, 동일결과 구간 최고 89.4%
- DB 연결 수 10으로 일정
- 가용 메모리 약 169~186MiB
- 디스크 큐 깊이 최고 약 0.0022로 매우 낮음
- Read IOPS 최고 약 1.43, Write IOPS 최고 약 1.28
- InnoDB buffer pool 물리 읽기 증가 0, 버퍼 적중률 100%
- Slow query 증가 0
- 혼합 구간 MySQL `Com_select` 증가 695,320
- 임시 디스크 테이블 증가는 6개뿐이며 디스크가 병목이 아님
- RDS 네트워크 송신 최고 약 4.96MB/s

현재 한계는 RDS CPU와 10개 Hikari 연결에서의 대기다. 데이터가 530개인 현 규모에서는 SQL 표현을 `ST_Within`에서 `MBRContains`로 바꾸는 것보다 실제 SPATIAL 인덱스 유지가 중요하다.

## 결론

1. 운영 기본 조회는 기존 `/emergencies/search`를 유지한다. SPATIAL 인덱스가 추가되어 기존 쿼리도 인덱스를 사용한다.
2. 실제 원형 반경과 거리순이 제품 요구라면 `/emergencies/search/optimized`를 사용하되 약 39%의 처리량 비용을 감수한다.
3. `/emergencies/search/indexed-bounds`는 기존과 동일 결과지만 성능 이점이 없어 비교/실험 경로로만 유지한다.
4. 다음 성능 개선 우선순위는 SQL 문법 변경보다 RDS 클래스 상향, Hikari 풀 조정, 정확 거리 결과 캐시 또는 가까운 후보 개수 제한이다.
